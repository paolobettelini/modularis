# Project overview

The repository has four important source areas:

```text
minecraft_simple_demo/
├── mods/           Rust crates used as APIs, providers, features, and contributors
├── modpacks/       Compile-time compositions
├── documentation/  This mdBook
├── build-client/   Generated client project
└── build-server/   Generated server project
```

`mods/` and `modpacks/` are the main source of truth. The build directories are
regenerated by Patchwork and should not be edited manually.

## Two applications, one domain

The client and server are separate Bevy applications:

```text
shared domain crates
       │
       ├── client.toml ──> Bevy window, input, rendering, client cache
       │
       └── server.toml ──> headless Bevy schedule, authority, world state
```

They share generated domain types:

- `BlockId`;
- `ItemId`;
- `ItemMetaSet`;
- `BlockMetaSet`;
- `Dimension`;
- network packet enums.

They do not share the same runtime implementations. For example, the client
uses a network sender that writes server-bound packets, while the server uses a
network sender that routes client-bound packets to addresses and player IDs.

## Main modpacks

The current compositions are:

| Modpack | Responsibility |
| --- | --- |
| `blocks.toml` | Block contributors, block metadata, generated block registry |
| `items.toml` | Item contributors, item metadata, generated item registry |
| `dimensions.toml` | Dimension contributors and generated `Dimension` enum |
| `biomes.toml` | Biome identity contributors and generated `BiomeId` enum |
| `network.toml` | Network message contributors and generated protocol |
| `common.toml` | Shared Bevy foundation plus blocks, items, and protocol |
| `client-vanilla.toml` | Optional Minecraft-like client behavior |
| `client-graphics.toml` | Optional lighting and voxel shading |
| `client.toml` | Playable client composition |
| `server-base.toml` | Neutral server transport and authoritative pipelines |
| `server-biomes-vanilla.toml` | Optional vanilla biome definitions, features, and selector |
| `server-vanilla.toml` | Optional Minecraft-like server rules and selected biome runtime/provider |
| `server.toml` | Demo server composition and concrete world providers |

The split between `server-base.toml` and `server-vanilla.toml` is especially
important. The base contains infrastructure such as TCP, packet routing,
sessions, inventory state, and chunk request handling. The vanilla pack adds
rules such as default loadouts, collision validation, block placement, portal
behavior, and grant-all flight.

## Runtime layers

The application can be viewed as five layers:

```text
Patchwork composition and code generation
                  │
Bevy app, schedules, resources, messages, components
                  │
Neutral domain services and authoritative state
                  │
Optional policy and vanilla behavior
                  │
Concrete client presentation and server world providers
```

The layers are intentionally crossed through small contracts. A network receive
mod should decode a request and emit an ECS message. It should not also decide
permissions, mutate the world, consume an item, and broadcast the result.

## Important generated crates

The repository contains development copies of generated crates:

- `generated-block-registry`;
- `generated-block-metadata`;
- `generated-item-registry`;
- `generated-item-metadata`;
- `generated-dimension-registry`;
- `generated-biome-registry`;
- `generated-client-settings-registry`;
- `generated-network-messages`.

Patchwork regenerates these from the final modpack. They make domain values
typed and exhaustive while still allowing the set of variants to change at
composition time.

For example, the current `BlockId` contains variants for air, dirt, grass,
stone, bedrock, crafting tables, ores, Nether blocks, Aether-related blocks,
and obsidian. Removing a contributor from the composition removes its generated
variant after recomposition.

## Current game features

The demo currently includes:

- TCP multiplayer with CBOR packets and length-prefixed framing;
- join, leave, timeout, movement, player visibility, and remote avatars;
- client-predicted first-person movement with server collision validation;
- configurable jump, sprint, flight, FOV, mouse sensitivity, and inventory key;
- vertically unbounded chunk coordinates with a moving client window;
- pluggable biome-driven Overworld, Nether, and Aether terrain providers;
- generated biome IDs with code-side definitions and phased world features;
- palette-compressed chunks carrying block instances and metadata;
- block breaking, item-based placement, reach checks, and hitbox checks;
- server-authoritative inventory, hotbar, stacking, quantity consumption, and
  drag/drop;
- shared cell menus, including a shared crafting-table grid;
- generated dimensions and generic portal rules;
- sky and sun synchronization;
- optional ambient light, shadows, face shading, and voxel ambient occlusion;
- Blocky/Hytale model and animation loading for remote players.

The implementation is intentionally small in visual scope, but the boundaries
are designed for replacement.
