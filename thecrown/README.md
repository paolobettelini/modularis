# TheCrown network

TheCrown combines independently deployable services:

- NATS as the message broker;
- `thecrown-relay` as the authoritative directory for physical game servers,
  logical instances, online players, transfers, and bans;
- `thecrown-web` as the standalone Actix + Leptos website;
- one `thecrown-auth` Modularis entry server on port `9999`;
- any number of `thecrown-game` Modularis workers, using port `10000` in the
  local development provider.

The website is not embedded in a game worker. Relay, web, auth, and game are
separate processes and communicate through shared protocol crates and NATS.

## Local topology

```text
client -> thecrown-auth:9999 -> Relay/NATS -> thecrown-game:10000
                                    ^                  |
                                    |                  |
                              thecrown-web:8080 <-------+
```

The auth server performs Patchwork account authentication, asks Relay for a
Hub, then transfers the client. The destination game worker independently
verifies the Patchwork account and redeems Relay's one-use cookie before it
admits the player to the exact instance.

## Prerequisites

- a NATS server available at `nats://127.0.0.1:4222`;
- Rust with edition 2024 support;
- `patchwork` in `PATH` for Modularis composition;
- for the web frontend, `wasm32-unknown-unknown` and `cargo-leptos`.

```sh
rustup target add wasm32-unknown-unknown
cargo install --locked cargo-leptos
```

## Relay

SQLite is the default database backend:

```sh
cd thecrown/thecrown-relay
cargo run -- --config relay.toml
```

Release build:

```sh
cargo build --release
./target/release/thecrown-relay --config relay.toml
```

MySQL build:

```sh
cargo run --no-default-features --features mysql -- --config relay.toml
```

Relay subscribes to `thecrown.relay`. A physical game worker subscribes to
`thecrown.gameserver.<server-id>` before publishing `RegisterServer`, ensuring
that immediate `StartInstance` packets are not lost.

The example `relay.toml` creates two initial instances for each mode whenever a
worker registers. The game worker itself always starts empty and only creates
the exact IDs supplied by Relay.

## Standalone web application

Development build and run:

```sh
cd thecrown/thecrown-web
cargo leptos build
cargo run --features server -- --config web.toml
```

Release build with embedded frontend assets:

```sh
cargo leptos build --release
cargo build --release --features server
./target/release/thecrown-web --config web.toml
```

MySQL:

```sh
cargo leptos build --release --no-default-features \
  --bin-features server,mysql --lib-features hydrate
cargo run --release --no-default-features --features server,mysql -- --config web.toml
```

The frontend uses Leptos SSR plus hydration. Debug assets are read from
`thecrown-web/dist`; release assets generated by `cargo leptos build --release`
are embedded in the server executable.

Frontend routes:

- `GET /`
- `GET /network`
- `GET /player`
- `GET /player/{identity}`
- `GET /auth/{token}`

API routes:

- `GET /health`
- `GET /api/me`
- `GET /api/online-players`
- `GET /api/player/{uuid}`
- `GET /api/debug`

## Modularis auth and game servers

From `minecraft_simple_demo/`:

```sh
patchwork compose --modpack thecrown-auth --modpacks-folder ./modpacks \
  --mods-folder ./mods --cache ./build-thecrown-auth

patchwork compose --modpack thecrown-game --modpacks-folder ./modpacks \
  --mods-folder ./mods --cache ./build-thecrown-game

patchwork compose --modpack client --modpacks-folder ./modpacks \
  --mods-folder ./mods --cache ./build-client
```

Start the game worker before clients enter through auth, then start auth and a
client:

```sh
cargo run --manifest-path build-thecrown-game/thecrown-game/Cargo.toml
cargo run --manifest-path build-thecrown-auth/thecrown-auth/Cargo.toml
cargo run --manifest-path build-client/client/Cargo.toml
```

Use `127.0.0.1:9999` as the client address. The local game configuration
advertises `127.0.0.1:10000`.

## Player admission

Entry flow:

1. auth obtains trusted UUID and username from Patchwork authentication;
2. auth requests `PlayerWantsToJoin { player }` from Relay;
3. Relay responds with `Ban`, `Unavailable`, or `Join { transfer }`;
4. auth kicks with the supplied reason or sends `TransferPlayer` to the client.

Destination flow:

1. client reconnects to the transfer address;
2. normal Patchwork authentication establishes the account identity;
3. client sends `AuthenticateTransfer`;
4. game requests `AuthUserJoin` with UUID, server ID, instance ID, and cookie;
5. Relay consumes the cookie and returns `ServeAuthResult`;
6. only `true` releases the client join gate and admits the player.

Auth never sends `RegisterServer`, `AuthUserJoin`, or `PlayerQuit`. It is not a
game location in Relay state.

## Instance lifecycle

Relay owns the mapping from exact `instance_id` to physical `server_id` and
sends:

- `GameServerPacket::StartInstance`;
- `GameServerPacket::StopInstance`.

Current modes are `Hub` and `Parkour`. A worker stores those exact IDs and does
not create instances at startup. Only empty instances may be stopped.

Hub instances share one scope for chat, visibility, and a world loaded entirely
into RAM from Modularis' native chunk format. The development world is stored
at:

```text
thecrown/data/hub/
  info.json
  data/chunk/index.bin
  data/chunk/regions/...
```

`thecrown/scripts/minecraft-world-converter` imports the Java Edition Anvil
world in `thecrown/scripts/minecraft_world` into this directory. Unsupported
blocks become stone; entities, block entities, fluids and other unsupported
Minecraft domains are intentionally not imported. The Hub path and spawn are
application policy in `thecrown-game-main-mod::hub`, while the chunk provider
only sees reusable in-memory `Chunk` values.

Parkour instances share chat but give each player a private visibility scope
and transient world.

## Transfer, whisper, and web commands

Game workers expose:

- `/hub` -> Relay chooses a Hub;
- `/play parkour` -> Relay chooses a Parkour instance;
- `/server <instance-id>` -> Relay chooses that exact instance;
- `/msg <username> <message>` -> Relay routes a cross-server whisper;
- `/weblogin` -> web service creates a one-use login token.

The web service can initiate a transfer through
`TrySendPlayerToSpecificServer`. Relay sends `ExecuteTransfer` to the physical
worker currently containing that UUID.

Whenever an authenticated player leaves or transfers, the source publishes
`PlayerQuit { player_uuid, server_id, instance_id }`. Relay ignores stale quit
messages if the player has already joined another location.

The client remembers the entry/auth endpoint while following a Relay transfer.
Returning to the Home screen restores that endpoint; a later Play action must
not reconnect directly to a game worker with an already consumed one-use
ticket.

## Parkour records

Parkour records are persisted in the existing `players.parkour_record` column.
The game worker loads and submits records through Relay protocol requests; it
does not connect to the database itself. Submissions only increase the stored
value, so reordered or stale scores cannot lower a player's personal best.

The player sees the current record after entering Parkour. A run is submitted
only when it ends because the player falls; intermediate checkpoints never
write the database. A confirmed improvement produces a chat message, and the
website reads the same database record for the player page.

## Configuration and persistence

- `thecrown-relay/relay.toml`: Relay policy, NATS, database, and logging;
- `thecrown-web/web.toml`: HTTP, sessions, NATS, database, and logging;
- `../modpacks/thecrown-auth.toml`: auth Modularis composition;
- `../modpacks/thecrown-game.toml`: game-worker composition;
- `data/thecrown.sqlite`: shared local SQLite database for the example configs.

Database migrations are under:

```text
mods/thecrown-database/migrations/sqlite
mods/thecrown-database/migrations/mysql
```

