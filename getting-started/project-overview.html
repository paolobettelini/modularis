Minecraft Simple Demo Architecture

Project overview

The repository has four important source areas:

minecraft_simple_demo/
├── mods/           Rust crates used as APIs, providers, features, and contributors
├── modpacks/       Compile-time compositions
├── documentation/  This mdBook
├── build-client/   Generated client project
└── build-server/   Generated server project

mods/ and modpacks/ are the main source of truth. The build directories are regenerated by Patchwork and should not be edited manually.

Two applications, one domain

The client and server are separate Bevy applications:

shared domain crates
       │
       ├── client.toml ──> Bevy window, input, rendering, client cache
       │
       └── server.toml ──> headless Bevy schedule, authority, world state

They share generated domain types:

  • BlockId;
  • ItemId;
  • ItemMetaSet;
  • BlockMetaSet;
  • Dimension;
  • network packet enums.

They do not share the same runtime implementations. For example, the client uses a network sender that writes server-bound packets, while the server uses a network sender that routes client-bound packets to addresses and player IDs.

Main modpacks

The current compositions are:

ModpackResponsibility
blocks.tomlBlock contributors, block metadata, generated block registry
items.tomlItem contributors, item metadata, generated item registry
dimensions.tomlDimension contributors and generated Dimension enum
biomes-{overworld,nether,aether}.tomlDimension-specific biome identity contributors
biomes.tomlAll demo biome identities and generated BiomeId enum
network.tomlNetwork message contributors and generated protocol
common.tomlShared Bevy foundation plus blocks, items, and protocol
client-vanilla.tomlOptional Minecraft-like client behavior
client-graphics.tomlOptional lighting and voxel shading
client.tomlPlayable client composition
server-base.tomlNeutral server transport and authoritative pipelines
server-biomes-{overworld,nether,aether}-vanilla.tomlOptional definitions and features for one dimension
server-biomes-vanilla.tomlUmbrella vanilla biome packs and selector
server-vanilla.tomlOptional Minecraft-like server rules and selected biome runtime/provider
server.tomlDemo server composition and concrete world providers

The split between server-base.toml and server-vanilla.toml is especially important. The base contains infrastructure such as TCP, packet routing, sessions, inventory state, and chunk request handling. The vanilla pack adds rules such as default loadouts, collision validation, block placement, portal behavior, and grant-all flight.

Runtime layers

The application can be viewed as five layers:

Patchwork composition and code generation
                  │
Bevy app, schedules, resources, messages, components
                  │
Neutral domain services and authoritative state
                  │
Optional policy and vanilla behavior
                  │
Concrete client presentation and server world providers

The layers are intentionally crossed through small contracts. A network receive mod should decode a request and emit an ECS message. It should not also decide permissions, mutate the world, consume an item, and broadcast the result.

Important generated crates

The repository contains development copies of generated crates:

  • generated-block-registry;
  • generated-block-metadata;
  • generated-item-registry;
  • generated-item-metadata;
  • generated-dimension-registry;
  • generated-biome-registry;
  • generated-client-settings-registry;
  • generated-network-messages.

Patchwork regenerates these from the final modpack. They make domain values typed and exhaustive while still allowing the set of variants to change at composition time.

For example, the current BlockId contains variants for air, dirt, grass, stone, bedrock, crafting tables, ores, Nether blocks, Aether-related blocks, and obsidian. Removing a contributor from the composition removes its generated variant after recomposition.

Current game features

The demo currently includes:

  • TCP multiplayer with CBOR packets and length-prefixed framing;
  • join, leave, timeout, movement, player visibility, and remote avatars;
  • unique-name admission using the generic client-visible kick pipeline;
  • configurable chat, audience-based delivery, Brigadier commands, and server-backed completion;
  • client-predicted first-person movement with server collision validation;
  • fixed-rate inertial movement with configurable jump, sprint, flight, separate flight speed, FOV, mouse sensitivity, and inventory key;
  • vertically unbounded chunk coordinates with a moving client window;
  • pluggable biome-driven Overworld, Nether, and Aether terrain providers;
  • an explicit scoped world-seed service used by procedural providers;
  • generated biome IDs with code-side definitions and phased world features;
  • palette-compressed chunks carrying block instances and metadata;
  • block breaking, item-based placement, reach checks, and hitbox checks;
  • server-authoritative inventory, hotbar, stacking, quantity consumption, and drag/drop;
  • shared cell menus, including a shared crafting-table grid;
  • generated dimensions and generic portal rules;
  • sky and sun synchronization;
  • optional ambient light, shadows, face shading, and voxel ambient occlusion;
  • Blocky/Hytale model and animation loading for remote players.

The implementation is intentionally small in visual scope, but the boundaries are designed for replacement.
